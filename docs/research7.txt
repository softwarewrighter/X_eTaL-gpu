
I have some ideas about future directions for softwarewrighter/X_eTaL.  (1) I want a way to generate FPGA programming files (verilog, etc.) to take some algorithm expressed in X_eTaL and implement dedicated circuits to do that calculation in FGPA instead of on CPU.  (2) I want to be able to compile some X_eTaL programs to run on older GPUs (not supported by latest CUDA). Worked for 16s
Your two goals fit X_eTaL unusually well because whole-array operations already expose parallelism and dataflow. I would not try to compile arbitrary X_eTaL to either FPGA or GPU initially. Define a deliberately constrained accelerator subset, lower it to one common IR, and give that IR multiple backends.

1. Architecture: one accelerator IR, several targets
I would evolve the compiler approximately like this:

                 X_eTaL source
                       │
                macros expanded
                       │
                  typed Core IR
                       │
             ┌─────────┴─────────┐
             │                   │
        normal evaluator    accelerator extraction
                                 │
                          Hardware/Dataflow IR
                            "XIR" perhaps
                                 │
              ┌──────────────────┼──────────────────┐
              │                  │                  │
          CPU/reference      OpenCL 1.2          RTL/Verilog
              │                  │                  │
              │              old GPU              Yosys
              │                                     │
              │                                  nextpnr
              │                                     │
              └────────────── validation ─────── FPGA
This fits the compiler you've already developed: lexer/parser → Core IR → static type inference → execution, rather than introducing a separate FPGA-oriented dialect.

The important new component is not a Verilog generator. It's the middle representation.

I'd tentatively call it XIR — X_eTaL Accelerator IR.

2. What belongs in XIR?
Make the first version tiny.

Something like:

enum Op {
    Input,
    Const,
    Add,
    Sub,
    Mul,
    Min,
    Max,
    Eq,
    Lt,
    Select,

    Map,
    Zip,
    Reduce,
}

Values carry information such as:

type:       i8 / i16 / i32 / f32
shape:      [1024]
operation:  add
inputs:     a, b
For example, conceptually:

a + b
might become:

%0 = input<i16>[1024] a
%1 = input<i16>[1024] b
%2 = map add<i16> %0 %1
return %2
This representation is simultaneously:

easy to interpret on the CPU;
easy to turn into a GPU kernel;
easy to turn into a hardware pipeline;
easy to display in your visual debugger;
easy to test against ordinary X_eTaL execution.
That last point is particularly valuable.

X_eTaL becomes the specification
For every accelerator program:

              X_eTaL
                │
          ┌─────┼──────┐
          ▼     ▼      ▼
       evaluator GPU   FPGA
          │       │      │
          └───────┼──────┘
                  ▼
            compare arrays
The existing evaluator is the golden reference implementation.

3. Don't compile all X_eTaL
This is probably the most important design decision.

FPGA synthesis wants static, bounded computation. GPUs want regular parallel work. So define an acceleratable region.

Initially accept:

statically known scalar types;
statically known rank;
preferably statically known dimensions;
pure functions;
arithmetic;
comparisons;
scalar extension/broadcasting;
each/map;
elementwise operations;
reductions;
perhaps inner shortly afterward.
Initially reject:

recursion;
arbitrary dynamic allocation;
arbitrary nested arrays;
dynamically determined shapes;
I/O;
native extensions;
most general higher-order functions;
anything whose hardware resources cannot be bounded.
That restriction isn't really alien to X_eTaL. Your static typing and explicit array/HOF vocabulary make it much easier to identify these computations than it would be in Python or C++.

4. FPGA backend: start embarrassingly small
Do not begin by trying to create an HLS compiler.

Start with:

X_eTaL
  ↓
Core
  ↓
XIR
  ↓
simple RTL generator
  ↓
Verilog
  ↓
Yosys
  ↓
nextpnr
  ↓
bitstream
Yosys supports the synthesizable Verilog-2005 subset and performs RTL/logic synthesis. 
 nextpnr then supplies portable place-and-route support for several FPGA families, including Gowin, which is interesting given your Tang Nano experimentation. 

First FPGA experiment
I'd make the first hardware function almost comically simple:

c ← a + b
where:

a : i16[8]
b : i16[8]
c : i16[8]
Generate eight adders.

Conceptually:

assign c0 = a0 + b0;
assign c1 = a1 + b1;
...
assign c7 = a7 + b7;

That demonstrates the key idea:

An X_eTaL array expression describes a spatial computation.

CPU interpretation:

for i:
    c[i] = a[i] + b[i]
GPU:

1024 work items
FPGA:

adder  adder  adder  adder
  │      │      │      │
 c[0]   c[1]   c[2]   c[3]
Same semantics, radically different realization.

That's a terrific X_eTaL demonstration.

5. Then introduce spatial vs temporal lowering
This becomes much more interesting when arrays are larger than available FPGA resources.

Suppose X_eTaL says:

c ← a + b
for 1024 elements.

The compiler could eventually choose:

Spatial
1024 adders
Huge area, potentially enormous parallelism.

Temporal
       ┌─────────┐
a ────►│         │
       │ ADDER   ├──► c
b ────►│         │
       └─────────┘
            ▲
            │
          counter
One adder reused 1024 times.

Tiled
16 adders × 64 cycles
That creates a fascinating compiler parameter:

xetal hw --lanes 1
xetal hw --lanes 4
xetal hw --lanes 16
xetal hw --lanes 1024
Same X_eTaL program.

Different physical implementation.

For your goals, this is more interesting than simply making it fast because you can visualize the transformation from array semantics into physical resources.

6. FPGA reductions become especially illustrative
Consider something analogous to:

+/ x
For eight values, the CPU implementation is approximately:

(((((((a+b)+c)+d)+e)+f)+g)+h)
But XIR can represent:

reduce add x
The FPGA backend can construct:

x0 ─┐
    +──┐
x1 ─┘  │
       +──┐
x2 ─┐  │  │
    +──┘  │
x3 ─┘     │
          +── result
x4 ─┐     │
    +──┐  │
x5 ─┘  │  │
       +──┘
x6 ─┐  │
    +──┘
x7 ─┘
Now X_eTaL's high-level array semantics directly produce a reduction tree.

This is exactly the sort of thing I'd want in an X_eTaL hardware demo.

7. Old GPU backend: target OpenCL C 1.2 first
For your legacy GPU collection, I'd deliberately avoid making CUDA the abstraction.

Use:

XIR
 ↓
OpenCL C 1.2
 ↓
vendor OpenCL compiler/runtime
 ↓
GPU
OpenCL C is specifically designed for kernels executing on OpenCL devices, and 1.2 remains part of the specification lineage. 

So:

c ← a + b
could produce approximately:

__kernel void xetal_kernel(
    __global const short *a,
    __global const short *b,
    __global short *c)
{
    size_t i = get_global_id(0);
    c[i] = a[i] + b[i];
}

The Rust host runtime then handles:

X_eTaL array
      ↓
host buffer
      ↓
device buffer
      ↓
OpenCL kernel
      ↓
device buffer
      ↓
X_eTaL array
This gives you exactly the conceptual demonstration you want without requiring the current CUDA ecosystem.

8. CUDA can become backend #3
I'd still add it eventually:

             XIR
              │
       ┌──────┼──────┐
       ▼      ▼      ▼
    Verilog OpenCL  CUDA C
But it is a worse first target for your "old hardware" objective because NVIDIA explicitly retires architectures from newer toolkits.

For example, NVIDIA currently lists:

Architecture	CC	Last CUDA toolkit
Kepler	3.5/3.7	CUDA 11.x
Maxwell	5.x	CUDA 12.x
Pascal	6.x	CUDA 12.x
Volta	7.0	CUDA 12.x
CUDA also doesn't guarantee binary compatibility across different major compute capabilities. 

So CUDA would force your X_eTaL project to know more about NVIDIA's historical toolchain matrix than I think you want.

Keep that mess below XIR.

11. I would make backend selection explicit initially
Don't start with an optimizer trying to determine where operations should execute.

Use something like:

xetal run --target cpu foo.xtl
xetal run --target opencl foo.xtl
xetal build --target verilog foo.xtl
Later you can introduce annotations/macros:

hw:fpga { ... }
hw:gpu  { ... }
or perhaps more X_eTaL-ish compile-time macros.

But I would resist adding these to the language now. Backend selection is initially a compiler/runtime concern, not language semantics.

That preserves the nice property:

X_eTaL meaning ≠ execution device
12. Types become surprisingly valuable
Static typing starts paying another dividend here.

Consider:

i8[16]
i16[16]
i32[16]
f32[16]
On CPU those distinctions matter somewhat.

On FPGA they're fundamental:

i8 + i8
      ↓
8-bit adder

i16 + i16
      ↓
16-bit adder
And eventually:

ternary
      ↓
specialized ternary datapath
That connects directly to your Tang Nano ternary-computer experiments and X_eTaL-ML ternary network.

A future X_eTaL type such as:

ternary[256]
could have completely different implementations:

CPU        packed representation
GPU        packed SIMD operations
FPGA       native -1/0/+1 datapath
Same semantic type, backend-specific physical representation.

That's much more compelling than merely emitting Verilog.

13. Suggested implementation sequence
I'd keep this aggressively incremental:

Milestone	Capability	Demonstrates
H0	Core → XIR dump	backend-neutral dataflow
H1	XIR interpreter	correctness/reference
G1	XIR → OpenCL map add	GPU offload
G2	map/sub/mul/select	useful GPU subset
G3	reduce	parallel algorithms
F1	XIR → Verilog scalar add	actual generated circuit
F2	fixed vector add	spatial array hardware
F3	configurable lanes	space/time tradeoff
F4	reduction tree	array semantics → topology
F5	synthesize/program FPGA	real hardware
H2	common CPU/GPU/FPGA tests	semantic equivalence
H3	visual hardware explanation	X_eTaL differentiator
I would not put matrix multiplication, CNNs, MoE, attention, etc. into the first milestone.

Get:

map
zip
reduce
working extremely well first.

Those three primitives already let X_eTaL express surprisingly rich hardware.

14. A very X_eTaL-specific opportunity
Eventually you can exploit something C/CUDA-derived HLS systems don't naturally have:

Shape is architectural information.
Given:

A : i16[4,4]
B : i16[4,4]
and an inner product, X_eTaL knows you're describing array algebra.

The backend can visualize alternative realizations:

X_eTaL
   │
   │ inner product

That's where this stops being merely "I wrote another HLS frontend".

The research/design question becomes:

How should an array expression become space, time, memory, and parallelism?

That's a very natural question for X_eTaL to explore.

How scheduling should work
This is where I think your project gets especially interesting.

Don't simply generate:

kernel_matmul(...)

Introduce a backend schedule separate from XIR semantics.

For example:

XIR:

    y = matmul(W, x)
can have:

CPU schedule
    rows = sequential
    cols = SIMD

GPU schedule
    rows = workgroups
    cols = workitems
    tile = 16x16

FPGA schedule
    lanes = 4
    MACs = 4
    stream weights
So:

                 matmul
                    │
             semantic XIR
                    │
        ┌───────────┼────────────┐
        ▼           ▼            ▼
     CPU sched   GPU sched    FPGA sched
        │           │            │
     loops       OpenCL        RTL
That scheduling layer is probably the architectural key to the entire project.

It separates:

what calculation is being performed

from:

how this particular machine performs it.

That's very much in the spirit of an array language.

And this connects directly to your old-GPU work
Suppose your model contains:

W : i8[4096,4096]
x : i8[4096]
The schedule could say:

device = P40
workgroup = 256
rows-per-group = 4
weight-storage = VRAM
activation-storage = VRAM
Or on an older 6 GB card:

device = GTX1660
workgroup = 128
weight-storage = host
weight-tile = 64MB
double-buffer = true
Eventually:

device = K80
weight-storage = host
tile = ...
The X_eTaL model doesn't change.

Only the schedule does.

That intersects strongly with what you've been exploring in moe-microscope and sw-os-ml: placement/scheduling of computation and model state across heterogeneous resources.

The three PoCs I'd target
PoC #1 — GPU plumbing: one X_eTaL map/reduce expression executes through OpenCL on an M40 or P40. CPU and GPU results match.

PoC #2 — "Jev on Jurassic hardware": a tiny transformer-like typed-decision model is trained from scratch; its inference implementation is ordinary X_eTaL array code; the exact same model and weights execute on CPU and an old GPU. Then visualize which X_eTaL operations became which GPU kernels.

PoC #3 — "Wrighting a calculator": calculator behavior is ordinary X_eTaL library code; hardwarewrighter/X_eTaL-fpga transforms that computation into Verilog, Verilator proves equivalence, Yosys/nextpnr/Apicula produce the bitstream, and a Tang Nano 4K physically becomes that calculator.

I particularly like #2 followed by #3 as demonstrations of the distinction you're making with the two GitHub organizations:

Softwarewrighter: take an array program and map it onto parallel hardware someone else designed.
Hardwarewrighter: take an array program and use it to describe the hardware itself.

Then the eventual #4 almost writes itself: take one layer of that same Jev-like model and ask X_eTaL-fpga to wright a physical accelerator for it. That closes the loop between the two projects.
