# X_eTaL-ML's benchmarks on GPUs

X_eTaL-ML's ask GA1 (its `docs/gpu-asks.md`): its batch programs,
from X_eTaL-ML c032768 (`XETAL_ML_COMMIT`), run by the pinned
X_eTaL 27b3fd0 (the reference) and as XIR programs on this
repository's interpreter and devices. Written by `scripts/ml-bench.py`
(`just ml-bench`) on `max`; whole-process times include reading
the data and, on a device, compiling the kernels. The device's time
is the kernels' own, from OpenCL profiling events, summed; the
launches' time is what the host waited from the first enqueue to
`finish`. Through the facade, the program runs under `xetal-x` with
the gpu extension, each call timed with `ck:t_ime`: the run is the
device's (compiling, uploading, the kernels, reading back), and the
bridge's cost is the bind and output calls, which carry the arrays
as text. The runtime builds the kernels on every run; vendor driver
caches may reduce compilation costs. There is no persistent runtime
session or resident weight cache yet. Kernel times omit setup,
transfers and the bridge; whole-process times show those costs.
Every result agrees with the evaluator: exactly on the interpreter,
within a relative 1e-5 on a device (f32). A device run is made twice
and the second reported, since the first after a change compiles the
kernels cold. These are single samples after warmup, not medians.
The evaluator and interpreter are reference implementations, not
optimized CPU library baselines. Compare each GPU with its own
host's evaluator; these totals do not isolate hardware throughput.

## The models

From the pinned X_eTaL-ML (c032768). The windows (the model's inputs) are generated by
the program's own core, run by the pinned xetal, and handed to the twin
with the weights from `data/`; the counts are Ints and are the same
everywhere, which is the ask's tolerance (f32 on this device).
